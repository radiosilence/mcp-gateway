# mcp-gateway

An OAuth-fronted gateway for self-hosted MCP servers: it authenticates the user once through Hydra and GitHub, then proxies each MCP with its stored credential injected. It ships as the image `ghcr.io/radiosilence/mcp-gateway` and the Pulumi component `@radiosilence/mcp-gateway-pulumi` in `deploy/pulumi`, which share one version; jaritanet deploys it by pinning that package.

## Git

- Work in PRs; never push to main. PRs are squashed; merge main into a branch rather than rebasing.
- Never push tags or publish the Pulumi package by hand. CI tags and publishes when a release PR merges.
- Commits are signed.

## Changelog

`CHANGELOG.md` is generated by `scripts/changelog.py` and never edited by hand. Every change adds one fragment under `changelog.d/unreleased/<section>/`, named `<pr>-<slug>.md` and holding one `- **Lead.** Detail.` entry; to correct a note, edit its fragment. `just changelog --stdout` previews the result. The format is in `changelog.d/README.md`.

## Releasing

`just release patch|minor|major` (or an exact `X.Y.Z`, or the Release workflow) branches from main, bumps `Cargo.toml`, `Cargo.lock`, `deploy/pulumi/package.json` and `APP_VERSION` in `deploy/pulumi/src/versions.ts`, turns the unreleased fragments into the version and opens the release PR. The three version strings must agree, since a pin on the package names exactly which gateway it deploys; CI refuses a release where they differ. Merging the PR is the release: CI pushes the `vX.Y.Z`, `vX.Y`, `vX` and `latest` image tags, then publishes the Pulumi package, then creates the GitHub release with the changelog section as notes. The GitHub release comes last because jaritanet's updater treats it as proof that the image and package exist. A push releases only when it changes the version; `gh workflow run ci-cd.yml` on main retries a release that failed part way.

```sh
just check   # fmt --check, clippy -D warnings, tests, actionlint
just fmt

```

The Pulumi component is checked separately: `npm ci && npm run check` in `deploy/pulumi`.

## CI/CD

`.github/workflows/ci-cd.yml` is one workflow in two halves. CI ends in `Checks`, the only status the ruleset requires; CD runs after it on main, in the same run, and ships what CI built.

The `changes` job decides from the diff which domains a change touches (`rust`, `web`, `package`, `docker`), and each CI job runs only for its domain, so a job skipping is expected: the change does not reach it. `Checks` passes when every job either passed or was skipped. Pull requests diff against their base; pushes to main against the last main commit whose run passed, and run everything when that commit cannot be found. A manual run, a release (a `release-*` branch or a version change) or a change under `.github/` runs everything. Markdown never counts.

Each domain is an allowlist of paths in `changes`. To add one, add its output and its `touches` line there, gate the new jobs on it with a job-level `if:`, and add them to `Checks`' `needs`. A new top-level directory of code is invisible to CI until a domain lists it.

The static binaries are built once per architecture (`build`), on pinned runners, and the image only copies them in (`container`, context `dist/`). Main pushes it as `:<sha>` during CI; CD moves `main` and `sha-<short>` onto it, and on a release the version tags.
